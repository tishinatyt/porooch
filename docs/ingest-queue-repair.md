# Восстановление очереди и площадок Karabas — 17.11.2026

## Что выяснено

Проверены реальные ссылки из каталога: `https://kyiv.karabas.com/`, `/concerts/`, `/theatres/`, `/child/`, `/stand-up/`. HTTP-клиент проверял robots.txt, отправлял PoruchBot и выдерживал паузу ≥2 секунд. UUID источников в локальном JSON не хранятся, поэтому сопоставление конкретного UUID с URL без базы не утверждается.

В четырёх разделах на странице две JSON-LD записи с одинаковым `@id`: короткая без location и полная с Place.name + PostalAddress.streetAddress. Парсер брал первую и исключал вторую как повтор external_id. Главная городская страница сразу содержит полную запись. Это воспроизведённая причина отсутствия площадок. Теперь @id разрешается до нормализации, поля объединяются; четыре реальные сокращённые фикстуры сохранены в tests/fixtures/karabas. На полученных страницах новый парсер дал: главная 203 уникальных валидных Event, каждый раздел 20; без места — 0 во всех пяти наборах. Это снимок, не обещание постоянного количества.

В локальном коде старое действие «все» уже не передавало IDs страницы и использовало LIMIT 100 / UUID; результат 25 по дате несовместим с этой версией. Точную версию исполнявшейся на проде функции/клиента без подключения установить нельзя. Новый отдельный RPC `poruch_moderation_filter_batch` не имеет аргумента IDs вообще. Он вызывает актуальную функцию с явным NULL и вычисляет done по наличию оставшихся UUID, а не по количеству на странице. UI получает общий count:exact из базы; тест проверяет 270 записей, 25 карточек и 3 порции для обоих действий. Новый SQL включает актуальное тело пакетной модерации, чтобы старое тело на проде тоже заменить.

Expire вызывался сборщиком до/после прохода, но использовал coalesce(ends_at, starts_at): начавшееся pending с будущим endDate оставалось в очереди. Админский клиент не вызывал expire, а прежний RPC был разрешён только service_role. Новый защищённый администраторский RPC вызывается перед загрузкой очереди. Pending истекает при starts_at<=now(); approved сохраняется до конца события. timestamptz сравнивает абсолютные моменты, включая корректное смещение Europe/Kyiv; усечения до календарного дня нет. Если сборщик давно не запускался/упал, новый вызов при загрузке всё равно очищает очередь.

## SQL и запуск

Вручную применить **docs/sql/ingest-queue-repair.sql** после event-source-scaling и миграции категории. SQL повторяемый, включает актуальные helpers/пакетную модерацию, новые фильтровый/expire RPC, безопасное дополнение фактов, объединение дублей и обновлённую запись сборщика. Идентичная миграция: `20261117140000_ingest_queue_repair.sql`. Чужие таблицы не затронуты. Изменения схемы/RPC требуют этого SQL; интерфейс сообщает имя файла при его отсутствии.

После применения и деплоя кода запустить существующий workflow вручную с **mode=backfill**, либо с ранее настроенными серверными секретами:

```powershell
node scripts/ingest/run.mjs --mode=backfill
```

Backfill читает pending/approved без площадки или координат порциями по 100 с UUID-курсором, перечитывает только ссылку события, проверяя robots, выбирает совпадающие название+время, дополняет место и геокодирует с прежним кешем. Проверка fingerprint защищает от перезаписи параллельной правки. Затем отдельными порциями объединяет существующие копии. Общий бюджет — 150 минут; deferred требует повторного запуска. Backfill не публикует pending автоматически и не обходит списки источников. Полный backfill в этой работе не запускался по запрету подключения к базе.

Новые события дедуплицируются по нормализованным названию + времени + городу; место не участвует. Из старых дублей выбирается самая полная активная запись, дополняются место/адрес, координаты, цена, валюта, обложка и source aliases/observations. Наличие ранее опубликованной копии сохраняет публикацию канонической записи. Остальные остаются rejected с причиной duplicate и duplicate_of, aliases переносятся на каноническую. Старые хеши не массово переписываются: SQL связывает наблюдения по новой идентичности и подставляет канонический hash, избегая конфликтов UNIQUE. Повторный запуск безопасен.

Поддержаны строковые location, Place без name с адресом, массивы и superEvent.location. Если в листинге место всё ещё отсутствует, обычный сбор дополнительно проверяет до трёх страниц событий на источник в пределах его тайм-аута; остальные может заполнить backfill. Запрещённые robots страницы не запрашиваются. Настоящее отсутствие места видно в модерации как «без місця». Город сам по себе больше не считается адресом площадки.

## Проверка

Сборка и 125 тестов прошли. Проверены 270 записей/3 порции в интерфейсе, все варианты location и реальные JSON-LD разделов, robots fallback, дедупликация при пустом месте, дополнение backfill, merge-курсор и статические правила SQL.
