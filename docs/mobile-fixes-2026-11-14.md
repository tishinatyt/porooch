## Доработка гонок

### EventChat

Экран имеет ключ пользователя/события, поэтому загрузки и подписки старого экземпляра не меняют новый чат, включая A→B→A и смену аккаунта. Realtime callbacks проверяют отмену подписки после async lookup.

Черновик, неизменный payload и состояние отправки вынесены в `src/lib/chatDelivery.ts`, отдельно для пользователя/события. Переход или unmount не отменяет начатую запись. Повторный submit блокируется синхронно. Черновики и неподтверждённый payload сохраняются в sessionStorage; при недоступном storage навигация по-прежнему сохраняет состояние в памяти.

UUID назначается перед первой отправкой и сохраняется для retry. Если ответ потерялся, pending payload остаётся и доступна явная повторная попытка. Повторный INSERT использует тот же первичный ключ; при duplicate key читается и проверяется существующее сообщение с теми же chat/sender/content. Повторной строки не создаётся. Новый черновик не стирается завершением старой операции. Успех/ошибка снимают sending в store независимо от того, открыт ли исходный экран. После успеха текущий чат перечитывается, а mergeMessages объединяет load/realtime по ID.

### useEvent

Используются отдельные последовательности загрузки события и участников плюс scope конкретного посещения маршрута. Старый A не может пройти проверку после A→B→A, даже если ID снова совпадает. Cleanup инвалидирует запросы; старые realtime/participation callbacks не обновляют другой scope. Результаты участников применяются только от последнего запроса. При смене ID прежние event/participants не возвращаются потребителю.

## Очистка QA

Скрипт требует `SUPABASE_URL`, `SUPABASE_ANON_KEY` и серверный `SUPABASE_SERVICE_ROLE_KEY`. Admin-доступ проверяется до создания fixtures; ключ не передаётся в браузер и не сохраняется в артефактах. Playwright нужен в окружении ручного QA-запуска; в зависимости проекта он не добавлялся. В этой задаче скрипт не запускался с настоящими клиентами.

- Пользователь регистрируется в списке сразу после получения ID, до проверки session и upsert. У anonymous identity есть уникальный marker запуска; cleanup находит по нему также signup с потерянным ответом.
- Event UUID заносится в registry до INSERT. `qa-artifacts/fixtures.json` сохраняет marker/IDs для восстановления после прерывания.
- `finally` закрывает браузер, завершает сессии и вызывает cleanup независимо от успешности UI-сценария. Удаляются события, public.users и Auth identities; связанные memberships/messages/read states удаляются существующими каскадами схемы.
- Каждый ресурс обрабатывается независимо, до трёх попыток, с проверкой отсутствия после удаления. Повторный cleanup допустим. Чужие данные не удаляются.
- Ошибка cleanup даёт ненулевой exit code и список ресурсов в `qa-artifacts/result.json`; артефакты исключены из Git. При недоступной базе или принудительном завершении процесса абсолютную очистку обещать нельзя: журнал позволяет восстановить список и повторить cleanup. Успешный результат не выдаётся при неудачной очистке.
